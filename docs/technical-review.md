# Технический разбор «Овертайм»

Документ для созвона: какие решения приняты, почему именно они, где границы демо и что
менять при росте. Это не README и не список фич, а карта компромиссов.

Состояние на 23.11.2026: Go/Fiber + Postgres + Vue 3, `docker compose up`, 52 Go-теста
(+21 подтест), 12 Vitest, oxlint, pre-push хук.

## 0. Карта системы

```
Браузер
  ├── REST  /api/session, /api/line, /api/bets, /api/bets/:id/settle-demo
  └── SSE   /api/stream  (snapshot, line, balance)
        │
      nginx :80  (same-origin, proxy_buffering off для SSE)
        │
      Fiber API :8080
        ├── betting.Service   правила ставки, лимиты, 409, demo settlement
        ├── line.Engine       in-memory линия, 2 источника, тик 3 с
        └── store            pgxpool, транзакции, ledger
              │
           Postgres 17
```

Деньги:

```
place bet:  lock player → idempotency lookup → insert bet → debit balance → insert ledger
settle:     lock player → lock bet → if win: credit payout + bet_win ledger; if loss: status only
```

Реалтайм:

```
engine tick → Snapshot → subscribers → SSE line event
bet settled → balance event (только при выигрыше)
```

## 1. Решения, о которых спросят «почему?»

### 1.1 Деньги и ставки

#### 1. Копейки в BIGINT, а не float/NUMERIC

**Выбор.** Все суммы — целые minor units (копейки) в `BIGINT`; коэффициенты — целые тысячные
(`1950` = `1.95`). `money.Payout` делает `stake × price / 1000` с проверкой переполнения и floor.

**Почему.** Деньги не должны зависеть от бинарного представления float. BIGINT даёт точные
сравнения, `CHECK (balance_minor >= 0)` и простую арифметику в Go и Postgres. Форматирование —
только на границе, через `Intl.NumberFormat`.

**Альтернативы.** `NUMERIC(14,2)` — точнее для мультивалютности, но тяжелее в Go и в JSON; float —
быстро, но недопустимо для денег; decimal-библиотека — лишняя зависимость для одной валюты.

**Цена.** Валюта фактически одна (RUB), minor units нужно помнить на каждом слое; в API нет
дробных сумм by design.

**Вопрос.** «Почему не хранить рубли с копейками в decimal?» — для демо достаточно BIGINT,
а `NUMERIC` понадобится при мультивалютности и разных scale.

#### 2. Баланс + append-only ledger в одной транзакции

**Выбор.** `players.balance_minor` — денормализованный текущий баланс; каждое изменение пишет
строку в `ledger_entries` с `amount_minor` и `balance_after_minor`. Ставка и списание — одна
транзакция; выигрыш — тоже одна транзакция.

**Почему.** Баланс читается за один SELECT, а ledger даёт аудит и возможность сверки. Запись
в ledger без изменения баланса (или наоборот) невозможна в одной транзакции.

**Альтернативы.** Считать баланс из ledger каждый раз — дороже и сложнее для горячего чтения;
event sourcing — сильнее, но избыточен для одной таблицы; Redis-баланс — быстрее, но добавляет
источник истины.

**Цена.** Два источника правды; нужна периодическая сверка `SUM(ledger) == balance` и запрет
прямых UPDATE вне сервиса. Сейчас это дисциплина, а не DB-триггер.

#### 3. `SELECT … FOR UPDATE`, а не optimistic locking

**Выбор.** Перед ставкой/расчётом блокируется строка игрока; ставка — ещё и строка bet.
Проверка баланса и idempotency идёт под блокировкой.

**Почему.** Один игрок — естественная точка сериализации; lock снимает гонки «проверили баланс →
списали дважды» и делает replay безопасным. Для одного демо-игрока конкуренции почти нет.

**Альтернативы.** Optimistic version column + retry — лучше при высокой конкуренции за одного
игрока, но добавляет цикл retry; SERIALIZABLE — сильнее, но дороже; Redis lock — ещё один
источник отказа.

**Цена.** Все ставки одного игрока сериализуются. При 100k ставок/с на одного игрока это станет
узким местом; для мультиплеера блокировка per-player нормальна.

#### 4. Idempotency key и replay **до** проверки цены

**Выбор.** Клиент присылает `idempotencyKey`; уникальный индекс `(player_id, key)`. Повтор
возвращает исходную ставку с `replayed: true`. В сервисе поиск существующей ставки стоит
раньше проверки `expectedPriceMilli`.

**Почему.** Пользователь может потерять ответ после успешного POST, повторить запрос — и не
должен получить второе списание. Если линия уже уехала, повтор всё равно должен вернуть
исходную ставку, а не `409`, который подтолкнёт клиента поставить ещё раз по новой цене.

**Альтернативы.** Redis-dedup с TTL — быстрее, но теряет историю; внешний idempotency service —
избыточен; «не повторять автоматически» — плохой UX.

**Цена.** Ключи живут в таблице bets; нужна политика retention. Сейчас ключ — UUID с клиента,
без TTL.

#### 5. `expectedPriceMilli` и 409 вместо тихого пересчёта

**Выбор.** Клиент присылает цену, которую видел; сервер сравнивает её с текущей. Расхождение —
`409 odds_changed` с новой ценой; UI показывает диалог «было → стало» и требует подтверждения.

**Почему.** Ставка — денежное обязательство; молчаливая замена цены нарушает доверие. 409
делает изменение явным и оставляет решение за пользователем.

**Альтернативы.** Принимать по последней цене — проще, но нечестно; tolerance ±N — компромисс,
но всё равно требует объяснения; блокировать кнопку на тик — хуже UX.

**Цена.** Лишний round-trip и диалог при движении линии; в проде можно добавить price lock на
1–2 секунды.

#### 6. Ручной demo settlement, а не автоматический

**Выбор.** `POST /api/bets/:id/settle-demo` разыгрывает pending-ставку с вероятностью `1/price`:
выигрыш зачисляет `potentialPayoutMinor` и пишет `bet_win`, проигрыш меняет статус. Игрок
нажимает «Демо-исход» в истории.

**Почему.** Бриф исключает автоматический расчёт после матча, но без исхода непонятно, прошла
ли ставка и что с деньгами. Ручной режим показывает win/loss и проверяет ledger, не изображая
реальный сеттлмент. Транзакция блокирует игрока и bet, поэтому двойного начисления нет.

**Альтернативы.** Автоматический scheduler по kickoff — вне скоупа и требует фида результатов;
вообще не добавлять — пользователь не видит результата; клиентская имитация — нечестно и
несогласованно с балансом.

**Цена.** Endpoint демо-уровня: без auth его нельзя выставлять в прод; исход случайный и не
хранит provider reference/время расчёта. В проде это отдельный settlement worker.

#### 7. Лимиты, floor и проверка переполнения

**Выбор.** Ставка 100–5 000 ₽, цена 1.05–20.00, payout floor до копейки, overflow guard.
DB-констрейнты дублируют часть правил.

**Почему.** Ограничения не дают одному запросу увести баланс/ответ в бесконечность; floor
гарантирует, что дом не заплатит больше математически рассчитанного. DB-проверки — последняя
линия обороны.

**Альтернативы.** Только UI-валидация — небезопасно; decimal rounding — дороже; округление
вверх — подарок игроку за счёт дома.

**Цена.** Щедрый игрок не может поставить больше 5 000 ₽ за раз; это демо-решение, а не
продуктовый лимит.

### 1.2 Линия и realtime

#### 8. Два источника → de-vig → blend 40/60 → margin 5% → floor

**Выбор.** `PulseBet` и `SharpLine` генерируют цены с разной overround (6% и 3%). Для каждого
источника снимается overround, векторы смешиваются с весами 0.4/0.6, затем применяется маржа
дома 5%, цена округляется вниз до сотых.

**Почему.** Сравнивать цены с разной маржой нельзя; de-vig приводит их к вероятностям.
Веса отражают, что sharp-источник точнее. Floor не даёт показать цену лучше модели, а значит
не съедает маржу на округлении.

**Альтернативы.** Один источник — проще, но не выполняет бриф; среднее цен — математически
неверно из-за overround; хранить вероятности в БД — нужно для аудита, но не для тика.

**Цена.** Вероятности считаются во float, затем цены фиксируются в milli. Если fair p > 95.238%,
цена на полу 1.05 уже выше справедливой; такой рынок закрывается (исход не показывается), а не
«поднимается» до 1.05. Для 90.7–95.238% floor может дать маржу ниже цели, но не убыток. UI маржу
не показывает, API отдаёт фактическую среднюю `marginBps` для отладки.

#### 9. Milli-odds вместо decimal

**Выбор.** Цена — целое `priceMilli`: 1950 = 1.95. Два знака — часть контракта.

**Почему.** JSON/БД не получают float-хвосты, сравнение цен точное, `expectedPriceMilli`
сравнивается как целое. UI форматирует в «2,10».

**Альтернативы.** Строки `"1.95"` — точнее, но неудобно считать payout; float — ошибки
сравнения; decimal — лишняя зависимость.

**Цена.** Нужна дисциплина: любая новая цена должна быть кратна 10 и проходить clamp.

#### 10. In-memory deterministic engine

**Выбор.** Линия живёт в памяти; `math/rand` с seed, фиксированный порядок обхода, тик 3 с.
`Snapshot()` возвращает глубокую копию; подписчики получают drop-oldest.

**Почему.** Это симуляция, а не фид: не нужны внешние API, БД на каждый тик и сетевые ошибки.
Seed делает линию воспроизводимой в тестах. 7 матчей × 3 исхода дёшево.

**Альтернативы.** Persisted markets в Postgres — нужно для реального сеттлмента и аудита, но
дороже на тик; Redis — быстрее, но ещё один компонент; реальный парсер — вне скоупа.

**Цена.** Рестарт сбрасывает линию и kickoff; несколько API-реплик дадут разные линии. Это
главное ограничение для масштабирования.

#### 11. SSE + полный снапшот на тик

**Выбор.** Один `EventSource` на `/api/stream`; на коннекте — `snapshot`, затем полный `line`
на каждом тике; `balance` после выигрыша; heartbeat 20 с. Клиент считает линию устаревшей
после 9 с без событий.

**Почему.** Поток однонаправленный, WebSocket не нужен. EventSource сам переподключается,
прокси понимает HTTP; полный снапшот идемпотентен — пропуск события не ломает состояние.
Для 7 матчей объём несущественен.

**Альтернативы.** WebSocket — двусторонний, но сложнее (heartbeat, reconnect, прокси); polling
— задержка/нагрузка; дельты — эффективнее, но нужен seq/буфер и обработка gap.

**Цена.** Каждый тик — полный JSON всем клиентам; при росте это первое, что упрётся в сеть/CPU.
`marginBps` и источники тоже едут в каждом снапшоте.

#### 12. Stale после 3 тиков, а не после первого reconnect

**Выбор.** При ошибке SSE показываем «Переподключение…», но не блокируем ставки сразу. Блокировка
— когда нет событий 9 с (три тика). Сервер всё равно проверит цену через `expectedPriceMilli`.

**Почему.** Короткий сетевой blip не должен выглядеть как сломанный продукт; последняя цена
остаётся доступной, но UI честно показывает состояние. Если цена ушла, сервер вернёт 409.

**Альтернативы.** Блокировать при `onerror` — безопаснее, но нервирует; не блокировать никогда
— рискованно; WebSocket ping — не отменяет необходимость staleness.

**Цена.** Окно до 9 с, когда можно нажать ставку по устаревшей цене; сервер её отклонит, но
пользователь получит диалог.

### 1.3 Бэкенд и данные

#### 13. Fiber + pgx + сырой SQL, без ORM

**Выбор.** Fiber v2 для HTTP, pgx/v5 для Postgres, SQL руками, `pgx.Tx` и `QueryRow`.

**Почему.** Нужны явные блокировки, порядок операций и контроль транзакций; ORM скрыл бы самое
важное. Схема маленькая, SQL читается. pgx — нативный драйвер, без `database/sql`-обёрток.

**Альтернативы.** `net/http`/chi — стандартнее, но больше boilerplate для SSE/JSON; GORM —
быстрее старт, но магические транзакции; sqlc — хороший компромисс на будущее.

**Цена.** Много ручного scan/повторяющегося SQL; нет compile-time проверки запросов; нужны
интеграционные тесты.

#### 14. Embedded migrations + advisory lock

**Выбор.** Один SQL-файл в бинаре, `schema_migrations`, транзакция + `pg_advisory_xact_lock` на
старте.

**Почему.** Миграции не нужно монтировать/запускать отдельно; advisory lock защищает от гонки
при нескольких репликах. Для одной схемы этого достаточно.

**Альтернативы.** golang-migrate/Atlas — версии, down, CLI; отдельный migration-job — правильнее
для CD; Flyway — если команда знает Java-инструменты.

**Цена.** Нет rollback/version tooling; миграция выполняется при старте API, а не отдельным
шагом; для больших изменений это плохой паттерн.

#### 15. Один demo-player и отсутствие auth

**Выбор.** `DemoPlayerID` захардкожен, все запросы работают от одного игрока; нет JWT/сессий.

**Почему.** Бриф прямо исключает регистрацию. Это позволяет сфокусироваться на деньгах,
линии и realtime, а не на identity.

**Альтернативы.** OIDC/Auth0 — больше кода и внешняя зависимость; signed session cookie —
проще, но всё равно лишний слой для демо.

**Цена.** Нет мультиплеера, авторизации SSE/ставок, лимитов на игрока; demo settlement открыт
любому, кто дотянется до API. В прод так нельзя.

#### 16. Единый JSON-конверт ошибок

**Выбор.** `{ "error": { "code", "message", "details?" } }`, коды `odds_changed`,
`insufficient_funds`, `stake_out_of_range`, `bet_not_pending` и т.д.

**Почему.** Клиент принимает решения по коду, а не по тексту; тексты можно менять/переводить.
HTTP-статусы stay conventional.

**Альтернативы.** RFC 7807 `application/problem+json` — стандарт, но для демо хватает своего
конверта; голые строки — плохо для типизации.

**Цена.** Свой конверт нужно документировать; нет автоматической OpenAPI-схемы.

### 1.4 Фронтенд

#### 17. Vue 3 composables + module state, без Pinia

**Выбор.** `useLine`, `useSession`, `useBets`, `useBetSlip` — модульные singleton-состояния на
`ref`; `src/api/*` — единственное место с URL/JSON/SSE.

**Почему.** Приложение маленькое; Pinia добавила бы зависимость и boilerplate. API-слой отделён,
логика ставки тестируема, компоненты тонкие.

**Альтернативы.** Pinia — devtools/масштабирование, но лишний слой; provide/inject — хуже
типизируется; глобальный store на reactive — ручной.

**Цена.** Модульные singleton’ы сложнее тестировать в изоляции и хуже масштабируются на много
доменов; при росте — Pinia или явные store-фабрики.

#### 18. Строгий типизированный API-слой

**Выбор.** Один `request()` с `ApiError`, типами ответов, таймаутом; EventSource — только в
`api/stream.ts`; компоненты не знают про fetch.

**Почему.** Ошибки/статусы/URL в одном месте; легче менять контракт и тестировать. `ApiError`
несёт code/details, что нужно для 409.

**Альтернативы.** OpenAPI-генератор — меньше ручных типов, но нужен spec/codegen; axios — не
даёт преимуществ; fetch в компонентах — размазывает контракт.

**Цена.** Типы написаны руками и могут разойтись с Go; нет contract-тестов/OpenAPI. При росте
это первый кандидат на генерацию.

#### 19. shadcn-vue + Tailwind v4 + ding + Magic UI + обычные Transition

**Выбор.** shadcn-vue на reka-ui, Tailwind v4, toast `@yusufceng1z/ding-vue`, порты
`NumberTicker`/`ShineBorder`/`GridPattern`, микровзаимодействия на Vue `<Transition>`.

**Почему.** Бриф задал shadcn/ding; shadcn даёт доступные примитивы в собственном коде, Tailwind
— скорость и токены; Magic UI — точечные эффекты без тяжёлой animation-библиотеки; Transition
достаточно для hover/flash/dialog.

**Альтернативы.** Vuetify/PrimeVue — быстрее старт, но чужой визуальный язык; framer-motion —
лишний вес для пары эффектов; CSS-in-JS — не вписывается в Tailwind.

**Цена.** Vendored shadcn-код нужно обновлять вручную; порты Magic UI — поддерживать; анимации
не должны мешать `prefers-reduced-motion`.

#### 20. Server-confirmed деньги, а не оптимистичный баланс

**Выбор.** Баланс обновляется из ответа POST/SSE; купон не списывает локально; 409 требует
явного подтверждения; сетевой retry идёт с тем же idempotency key.

**Почему.** Деньги важнее мгновенности. Оптимистичное списание может показать баланс, которого
нет; повтор с новым ключом — двойная ставка.

**Альтернативы.** Оптимистичный UI + rollback — быстрее, но сложнее и рискованнее; локальный
расчёт баланса — неверно при других вкладках.

**Цена.** Кнопка ждёт сервер; при медленной сети нужен in-flight state и понятные ошибки.

### 1.5 Инфраструктура и процесс

#### 21. Docker Compose + nginx same-origin

**Выбор.** `db` + `api` + `web`; nginx отдаёт SPA и проксирует `/api` на `api:8080`, SSE без
буферизации; один `docker compose up`.

**Почему.** Бриф требует одну команду. Same-origin убирает CORS и делает SSE/cookies проще;
nginx уже умеет отключать буферизацию для потока.

**Альтернативы.** Отдельные origin с CORS — больше конфигурации; K8s/Ingress — вне скоупа;
Vite preview — не для SSE-прокси.

**Цена.** Нет TLS/HA/автоскейла; фиксированный host-порт БД (5437) может конфликтовать; nginx
не сжимает статику (gzip не настроен). Для локалки/демо это нормально.

#### 22. Тесты: TDD-бэкенд, изолированные схемы, race; фронтенд — чистые функции

**Выбор.** Backend-тесты писались до реализации отдельным агентом: unit-математика + интеграция
с Postgres в уникальной схеме + `-race`. Frontend — Vitest на форматтеры/валидацию/idempotency;
UI проверяется Playwright вручную. oxlint + pre-push.

**Почему.** Деньги и конкурентность нельзя проверять моками; реальная схема ловит CHECK,
уникальные индексы и блокировки. Уникальная схема на тест позволяет `go test ./...` без гонки
между пакетами. 12 фронтовых тестов покрывают то, что легко сломать и дешево тестировать.

**Альтернативы.** Только unit-тесты с моками — быстрее, но не поймает SQL/локи; только
Playwright — медленно и хрупко; testcontainers — ближе к CI, но требует Docker.

**Цена.** Интеграционные тесты требуют Postgres и `TEST_DATABASE_URL`; без него skip. Нет
компонентных/E2E тестов в CI; pre-push можно обойти `--no-verify`. Это следующий шаг, а не
«всё покрыто».

## 2. Быстрые ответы на вопросы

| Вопрос | Короткий ответ |
| --- | --- |
| Почему не float для денег? | Float теряет копейки и ломает `balance >= 0`; BIGINT + floor + overflow guard. |
| Почему `BIGINT`, а не `NUMERIC`? | Одна валюта, простые вычисления в Go/JSON; `NUMERIC` — при мультивалютности. |
| Почему row lock, а не optimistic? | Один игрок — естественная сериализация; проще доказать отсутствие двойного списания. |
| Почему replay **до** цены? | Потерянный ответ не должен превращаться в 409 и вторую ставку по новой цене. |
| Почему не принять новую цену молча? | Это денежное обязательство; 409 даёт пользователю выбор, UI показывает «было → стало». |
| Почему два источника и веса 40/60? | Разный overround нельзя сравнивать напрямую; de-vig + sharp-вес точнее одного источника. |
| Почему floor, а не round? | Floor никогда не даёт игроку цену лучше модели; маржа не съедается округлением. |
| Почему линия в памяти? | Это симуляция; seed + отсутствие внешнего фида; 7 матчей дёшево. Рестарт сбрасывает. |
| Почему SSE, а не WebSocket? | Поток односторонний, EventSource сам переподключается, проще с nginx/SSE. |
| Почему полный снапшот? | Пропуск события безопасен, клиент проще; дельты — следующий шаг при росте. |
| Почему Fiber? | Быстрый HTTP и удобный stream для SSE; меньше boilerplate, чем net/http. |
| Почему без ORM? | Нужны явные `FOR UPDATE`, транзакции и контроль SQL; схема маленькая. |
| Почему нет Pinia? | Приложение маленькое; composables + API-слой дешевле; Pinia — при росте домена. |
| Почему нет auth? | Бриф исключает регистрацию; один demo-player. В прод — OIDC + authz на SSE и ставки. |
| Почему ручной settlement? | Автосеттлмент вне брифа, но без win/loss непонятно; ручной endpoint проверяет ledger и locks. |
| Почему нет автосеттлмента? | Нет фида результатов/рынков; для прода нужен worker, market versions и outbox. |
| Что не тестируется? | Компонентный UI/E2E в CI, нагрузка SSE, миграции на больших данных, security. |
| Что сломается при 2 репликах? | In-memory линии разойдутся; SSE-клиенты увидят разные цены. Нужен общий line service. |

## 3. Риски и техдолг

| Приоритет | Риск | Влияние | Что делать |
| --- | --- | --- | --- |
| P1 | In-memory line + single API replica | Горизонтальное масштабирование даёт разные линии | Вынести линию в общий сервис, снапшоты в Redis/NATS |
| P1 | Demo settle endpoint без auth | Любой клиент может рассчитать pending-ставку | Убрать из prod или закрыть admin/auth-флагом |
| P1 | Нет DB-уникальности на `bet_win` per bet | Двойное начисление возможно только при обходе status+lock | `UNIQUE (bet_id, kind)` / settlements table |
| P2 | Нет bet/status SSE-событий | Другая вкладка не видит won/lost, история stale | `bet.settled` event + invalidation |
| P2 | `replayBet` читает bet и balance двумя запросами | Возможен несогласованный снимок для ответа | Read-only tx/один JOIN |
| P2 | Full snapshot × clone на каждого подписчика | CPU/сеть при 100+ клиентах | Дельты, shared JSON, pub/sub gateway |
| P2 | Нет CI; pre-push локален | Можно обойти `--no-verify`, нет PR-гейта | GitHub Actions: tests/lint/build/e2e |
| P2 | Lockfile содержит ручные `@emnapi` записи | `npm install` может снова их вычистить | Обновить npm/политику lock; проверять `npm ci` в CI |
| P2 | Docker: floating tags, фиксированный 5437, hardcoded creds | Невоспроизводимость/конфликты/секреты | Digest-pin, env secrets, dynamic port |
| P3 | `currencyRUB` в ответах захардкожен | Мультивалютность сломается | Брать `player.Currency` |
| P3 | Нет retention/partitioning ledger/bets | Рост таблиц и индексов | Партиции по месяцу, архивирование, TTL ключей |
| P3 | `marginBps` — средняя фактическая маржа по рынкам, не per-market отчётность | Нельзя использовать как финансовый отчёт по каждому рынку | Считать per-market, хранить snapshot версии |
| P3 | Закрытый рынок просто исчезает из линии | Игрок не понимает, почему матча нет | Добавить `status=suspended/closed` и сообщение |
| P3 | Demo settlement без `settled_at`/provider ref | Нет аудита исхода | `settlements` table с результатом и временем |
| P3 | Рынок не закрывается на старте матча | После kickoff ставка всё ещё может быть принята | Закрывать market по фиду/таймеру; статус live/settled |
| P3 | 8px бейдж лиги | Мелкий текст, a11y-риск | Вернуть 9–10px при переработке сетки |
| P3 | Нет rate limit/CSP/security headers/TLS | Публичный прод уязвим | Gateway/WAF, CSP, TLS, лимиты |
| P3 | Нет request id/tracing | Сложно расследовать инциденты | OTel + structured access logs |
| P3 | Нет OpenAPI/contract tests | Ручные типы расходятся с Go | OpenAPI + codegen/contract test |

## 4. Масштабирование (отдельный блок)

### 4.1 Что сломается первым

| Нагрузка | Узкое место | Почему | Решение |
| --- | --- | --- | --- |
| 10× матчей | Размер полного snapshot | 70×3 исходов + источники в JSON каждые 3 с | Дельты по market, сжатие, per-league каналы |
| 100× клиентов | SSE fan-out | Клонирование всего snapshot на каждого подписчика | Shared immutable snapshot + pub/sub gateway |
| 2+ API | In-memory line | Каждая реплика генерирует свою линию | Line service + Redis/NATS, API stateless |
| 100× ставок | Блокировки/БД | Один player-lock и один Postgres primary | per-player locks, PgBouncer, read replicas, partitions |
| Автосеттлмент | Нет scheduler/feed | Ручной `/settle-demo` не является сетевым расчётом | Settlement worker, provider adapters, outbox |
| Мультиплеер | Нет auth | Все запросы — demo-player | OIDC, player id, authz, limits |
| Рост команды | Нет CI/CD | Локальный pre-push, ручной деплой | CI, contract/e2e, image digests, migration job |

### 4.2 Целевая схема

```
                    ┌──────────────┐
  clients ──TLS──▶  │ API Gateway  │  auth, rate limit, CSP, SSE/WS
                    └──────┬───────┘
                           │
          ┌────────────────┼────────────────┐
          ▼                ▼                ▼
    API replicas      SSE gateway      Settlement worker
    (stateless)       (fan-out)        (idempotent commands)
          │                │                │
          └────────┬───────┴────────┬───────┘
                   ▼                ▼
               Redis/NATS        Postgres
             line snapshot      bets, ledger,
             + pub/sub          markets, outbox,
                                settlements
                   ▲
             Line service
       providers → normalize → de-vig → blend → margin
                   │
              Provider adapters
```

Ключевой сдвиг: **линия перестаёт быть частью API-процесса**. API становится stateless; линия —
отдельный сервис с общим снапшотом и pub/sub. Это убирает расхождение реплик и позволяет
масштабировать SSE отдельно от ставок.

### 4.3 Данные

Добавить версионирование рынка, чтобы ставка ссылалась не на строку, а на версию:

```sql
fixtures(id, league, home, away, starts_at, status)
markets(id, fixture_id, kind, version, margin_bps, created_at)
outcomes(id, market_id, key, price_milli, source_prices, created_at)
bets(id, player_id, market_id, outcome_id, market_version_id, price_milli, ...)
settlements(id, bet_id unique, result, provider_ref, settled_at)
ledger_entries(..., unique (bet_id, kind))  -- bet_win ровно один
outbox(id, aggregate_type, aggregate_id, payload, published_at)
```

- `bets.market_version_id` — аудит: по какой цене/версии принята ставка.
- `settlements` — идемпотентный результат, а не только `bets.status`.
- `ledger_entries` unique для win — защита от двойного начисления на уровне БД.
- `outbox` — атомарно «изменил bet + отправил событие», без dual-write.
- Партиции `ledger_entries`/`bets` по месяцу; retention idempotency keys.
- `PgBouncer` перед Postgres, read replica для истории, primary для записи.

### 4.4 Realtime

- **Дельты.** `line.delta` с `seq`, `market_id`, `outcome_prices`; `Last-Event-ID`; периодический
  полный snapshot (раз в N секунд) для восстановления.
- **Каналы.** Подписка на лигу/спорт, а не на весь мир; клиент получает только видимые матчи.
- **Fan-out.** Redis pub/sub/NATS → SSE gateway; API не держит подписчиков линии в памяти.
- **Backpressure.** Ограничение соединений на инстанс, буфер на клиента, политика drop-oldest
  (уже есть) + метрика дропов; медленный клиент не тормозит тик.
- **События ставки.** `bet.placed`, `bet.settled`, `balance` — per-player канал; тогда вторая
  вкладка видит won/lost и баланс без reload.
- **WebSocket.** Рассмотреть, если появится двусторонний поток (чат/лайв-ставки); сейчас SSE
  достаточно.

### 4.5 Деньги и риск

- **Settlement worker.** Читает результаты фида, находит market version, идемпотентно создаёт
  `settlements` и проводки; unique constraints + outbox.
- **Double-entry.** Не только один player-ledger: счета house/player/exposure; баланс — сумма
  проводок; ежедневная сверка.
- **Лимиты.** Max payout на ставку/рынок/игрока, exposure по исходу, stake limits, cooldown;
  risk engine до принятия ставки.
- **Audit.** `settled_at`, provider reference, версия рынка, who/what/why.
- **Demo endpoint.** В prod отсутствует или закрыт admin-auth и feature flag; сейчас это
  демонстрационный инструмент.
- **Reconciliation.** Регулярная сверка ledger ↔ balance ↔ settlements, алерты на расхождение.

### 4.6 Ops и безопасность

- **CI/CD.** GitHub Actions: Postgres service, `go test -race`, frontend lint/typecheck/test/build,
  Playwright smoke, image build, migration test; pre-push остаётся быстрым локальным гейтом.
- **Images.** Digest-pin, SBOM, non-root, read-only FS, resource limits, separate migration job.
- **Secrets/TLS.** Не хранить пароли в compose; Vault/SM; TLS на gateway; HSTS/CSP/security headers;
  CORS только для разрешённых origin.
- **Rate limit/WAF.** По IP/player/route; защита `/bets` и `/settle-demo`; idempotency + anti-abuse.
- **Observability.** OTel traces, Prometheus metrics (tick duration, SSE connections, drops,
  DB pool, settlement failures, bet p99), structured logs с request id, алерты.
- **Backups/PITR.** Ежедневные бэкапы + point-in-time recovery; регулярный restore drill.

### 4.7 Frontend

- **Bet events** через SSE: `bet.placed/settled` → обновление истории и баланса во всех вкладках.
- **Виртуализация** списка матчей при 100+; мемоизация строк; не пересчитывать все карточки на
  каждый тик.
- **State**: при росте — Pinia/доменные store-фабрики; сейчас composables осознанно.
- **Контракты**: OpenAPI → сгенерированные типы/клиент, contract tests против Go.
- **Качество**: component tests + Playwright в CI, a11y-аудит, i18n, CSP, бюджеты бандла.
- **UX**: экран «как считается ставка/выплата», история рынка, фильтры, статус расчёта.

### 4.8 Порядок внедрения

| Этап | Что сделать | Зачем |
| --- | --- | --- |
| 0. Сейчас | unique `(bet_id, kind)` для win, убрать/закрыть demo settle в prod, bet SSE, CI, метрики, digest-pin | Закрыть денежные и операционные риски |
| 1. 10× | Line service + Redis/NATS, дельты SSE, market persistence/versioning, auth/multi-player | Убрать расхождение реплик и рост snapshot |
| 2. 100× | Settlement worker/outbox, exposure/limits, PgBouncer/read replica/partitions, load tests | Выдержать ставки/расчёты и объём ledger |
| 3. Дальше | Multi-region, provider failover, compliance/audit, WebSocket при необходимости | География, надёжность, регуляторика |

Приоритет: **деньги → консистентность линии → наблюдаемость → масштаб**. Красивые дельты SSE
не нужны, если settlement может начислить дважды; сначала constraints и аудит.

## 5. Что оставил бы без изменений

- Целые копейки, floor payout, overflow guard.
- Ledger + транзакция + `FOR UPDATE` per player.
- Idempotency до проверки цены и 409 на изменение.
- Де-виг двух источников, веса 40/60, floor цен.
- SSE snapshot-on-reconnect + stale-политика.
- Разделение `api/` и `composables/`, тонкие компоненты.
- TDD-набор на деньги/линию/SSE и schema-isolated integration tests.
